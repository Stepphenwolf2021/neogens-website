ทุกข้อในไฟล์นี้มาจากความผิดพลาดจริงที่เกิดขึ้นกับโปรเจกต์นี้ ไม่ใช่กฎที่คิดขึ้นลอย ๆ
ไฟล์นี้เพิ่มได้เรื่อย ๆ ห้ามลบข้อเก่าออกแม้จะรู้สึกว่าไม่พลาดอีกแล้ว

**จำนวนบทเรียนตอนนี้ 15 ข้อ**

Claude ต้องอ่านไฟล์นี้จนจบก่อนตอบอะไรก็ตามในโปรเจกต์นี้ แล้วขึ้นต้นข้อความแรกของเซสชันด้วยบรรทัดนี้

## 1 · อย่าสรุปสถานะงานจากเอกสารใน Context ให้ไปดูของจริงก่อน

**เกิดขึ้น 2026-08-14** Noppadol ถามว่า "สรุปงานเว็บไซต์ที่ค้างอยู่" Claude อ่านเอกสารรากฐานใบเดียวที่อยู่ใน Context แล้วตอบว่ายังไม่ได้ลงมือทำเว็บเลย ยังเหลืออีก 6 ข้อที่ต้องตัดสินใจก่อนเริ่ม

ความจริงคือ `neogens.co` ขึ้นไปนานแล้ว เป็นเว็บ 13 หน้าต่อภาษา สองภาษา มีธีมสลับ มีบทความยาว มี `check.command` และ `publish.command` ใช้งานได้จริง Claude สรุปผิดทั้งหมด เพราะเอกสารใน Context เขียนไว้ตั้งแต่ก่อนลงมือ แล้วไม่มีใครไปอัปเดตมัน

**นี่คือหลักการข้อ 6 ของบริษัทเอง** แผนที่ไม่ใช่ดินแดน Claude อธิบายทุกอย่างได้อย่างสมเหตุสมผลจากแผนที่ที่ล้าสมัย

**กฎ** ก่อนตอบคำถามว่า *ค้างอะไร* หรือ *สถานะเป็นอย่างไร* หรือ *ทำอะไรไปแล้วบ้าง* ต้องทำสามอย่างนี้ก่อน ห้ามข้าม

1. อ่านไฟล์จริงในรีโป และดู `git log`
2. เปิด `neogens.co` ของจริงขึ้นมาดู
3. ไล่ transcript เซสชันเก่าที่เกี่ยวข้อง ด้วย `list_sessions` แล้ว `read_transcript`

เอกสารใน Context บอกได้แค่ว่าเคยตั้งใจจะทำอะไร ไม่ได้บอกว่าทำไปแล้วแค่ไหน

## 2 · อ่านสคริปต์ให้จบก่อนให้คำแนะนำเรื่องสคริปต์

**เกิดขึ้น 2026-08-14** Claude เห็นโฟลเดอร์ `card/` ที่ยังไม่ถูก track แล้วเตือนว่า `publish.command` ใช้ `git add -A` เดี๋ยวจะกวาดไฟล์นามบัตรขึ้น GitHub ด้วย พร้อมเสนอให้ Noppadol ย้ายโฟลเดอร์ออกเองหรือแก้ `.gitignore` ก่อน

แต่ `.tools/publish.sh` มีด่านนี้อยู่แล้วตั้งแต่ต้น ขั้น 3/5 มันโชว์ diff stat แล้วพิมพ์ว่า "Read the list above. If you see a file you did not mean to touch, answer N" ถ้าตอบ N มันจะ `git reset` คืนให้เอง Claude สั่งงานซ้อนกลไกที่ออกแบบมาเพื่อเรื่องนี้พอดี เพราะอ่านแค่บรรทัด `git add -A` แล้วหยุด

**กฎ** ก่อนพูดถึงพฤติกรรมของ `check.command` `publish.command` `.tools/publish.sh` หรือ `.tools/check.py` ต้องอ่านไฟล์นั้นทั้งไฟล์ก่อน ห้าม grep แล้วเดาจากบรรทัดเดียว

**กฎที่ตามมา** วิธีทำงานที่ตกลงกันไว้คือ Noppadol ดับเบิลคลิก `check.command` แล้วตามด้วย `publish.command` ไม่ใช่พิมพ์คำสั่งใน terminal อย่ายื่นคำสั่ง git ให้เขารันเอง นอกจากเขาจะขอ และ Claude แก้ไฟล์อย่างเดียว ไม่ commit ไม่ push

## 5 · ด่านบังคับต้องผ่านก่อนพิมพ์ตัวอักษรแรก ไม่ใช่ก่อนแก้ไฟล์

นั่นคือความผิดข้อ 1 คำต่อคำ ทั้งที่ข้อ 1 ถูกเขียนขึ้นเพราะความผิดอันนี้พอดีเมื่อวันก่อนหน้า

สาเหตุที่ด่านไม่ทำงานคือ Claude ตีความคำว่า "ก่อนเริ่มงาน" เป็นก่อนแก้ไฟล์ ไม่ใช่ก่อนพูด จึงทักทายและสรุปสถานะไปก่อน แล้วค่อยไปอ่านทีหลัง **แต่ความเสียหายของข้อ 1 เกิดที่ประโยคแรก ไม่ได้เกิดที่การแก้ไฟล์**

## 6 · `git status` กับ `git diff` ไม่ใช่คำสั่งอ่านอย่างเดียว มันทิ้งไฟล์ล็อคไว้

**เกิดขึ้น 2026-08-15** Claude รัน `git diff --stat` เพื่อตรวจงานตัวเองว่าแก้อะไรไปบ้าง คำสั่งนั้นสร้าง `.git/index.lock` ขึ้นมาแล้วลบตัวเองไม่ได้ เพราะสิทธิ์ในกล่องที่ Claude รันคำสั่งไม่ตรงกับสิทธิ์บนเครื่อง ตอนนั้นมี warning ขึ้นว่า `unable to unlink .git/index.lock` แต่ Claude อ่านผ่านไป

ผลคือ Noppadol กด `publish.command` แล้วมันตายที่ขั้น 3/5 ว่า **`Unable to create '.git/index.lock': File exists`** เสียเวลาเปล่าไปหนึ่งรอบ กับความผิดที่ตัวเองก่อไว้เงียบ ๆ ตั้งแต่ก่อนหน้านั้น

`git status` และ `git diff` หน้าตาเหมือนคำสั่งที่แค่อ่าน แต่ทั้งคู่เขียน `index.lock` ตอน refresh index ส่วน `git log` กับ `git show` ไม่แตะ index จึงปลอดภัย

**กฎ** ถ้าต้องเรียก `git status` หรือ `git diff` ในโปรเจกต์นี้ ให้ใส่ `--no-optional-locks` เสมอ

```
git --no-optional-locks status --short
git --no-optional-locks diff --stat
```

**กฎที่ตามมา** ก่อนจบทุกครั้งที่แตะ git ให้เช็กว่า `.git/index.lock` ไม่มีอยู่ ถ้ามีต้องลบก่อนบอกว่างานเสร็จ และเจอ warning จาก git เมื่อไร ห้ามอ่านผ่าน เพราะข้อ 4 ของบริษัทเองเขียนไว้ว่าความเงียบคือศัตรู ตรงนี้ git ส่งเสียงเตือนแล้ว คนที่เงียบคือ Claude

## 7 · เวลาของพัง ให้ถามก่อนว่าเปิดจากที่ไหน อย่าเพิ่งไปไล่ทฤษฎี

**เกิดขึ้น 2026-08-15** ฟอร์มบนหน้ากาแฟส่งไม่ผ่าน Claude ไล่หาสาเหตุอยู่สามรอบ ตั้งทฤษฎีว่าเป็นการจำกัดอัตรา 429 แก้ Worker ขยับโควตาจาก 5 เป็น 20 เขียนเทสต์เพิ่ม แล้วให้ Noppadol deploy ใหม่

พอขอภาพหน้าจอ Network tab มาดู คำตอบอยู่บนแถบที่อยู่บรรทัดแรกสุด — เขาเปิดไฟล์ด้วย `file:///Users/...` ไม่ใช่จาก `https://www.neogens.co` หน้าที่เปิดแบบนี้ส่ง Origin เป็น `null` Worker จึงตีกลับเป็น CORS error ตั้งแต่ด่านแรก **ไม่ใช่บั๊ก และไม่มีอะไรต้องแก้เลย**

**สิ่งที่ทำให้เรื่องนี้แย่กว่าการเดาผิดธรรมดา** คือ Claude เขียนคำเตือนเรื่องนี้ไว้เองในรายงานก่อนหน้า คำต่อคำว่า *"ฟอร์มจะไม่ทำงานถ้าเปิดไฟล์จากเครื่อง เปิด local จะได้ 403"* แล้วพอมันเกิดขึ้นจริง กลับไม่ได้ย้อนไปอ่านสิ่งที่ตัวเองเพิ่งเขียน

**กฎ** เจอรายงานว่าของบนเว็บพัง คำถามแรกคือ **เปิดจาก URL ไหน** ถามก่อนตั้งทฤษฎีใด ๆ ทั้งสิ้น และก่อนแก้โค้ดแม้แต่บรรทัดเดียว

**กฎที่ตามมา** ขอหลักฐานตรง ๆ ก่อนเดา — ภาพหน้าจอ Network tab หรือค่าสถานะจริง ใช้เวลาน้อยกว่าการไล่ทฤษฎีมาก และอย่าลืมย้อนอ่านคำเตือนที่ตัวเองเขียนไว้เองในบทสนทนาเดียวกัน

## 8 · ตั้งชื่อคลาส CSS ใหม่ ต้อง grep ก่อนว่าชื่อนั้นมีอยู่แล้วหรือยัง

**เกิดขึ้น 2026-08-15** Claude จัดหน้า `about.html` ใหม่ แตกบล็อก story ยาวเป็นสองคอลัมน์ ตั้งชื่อคลาสว่า `split` แล้วเขียนกฎ `.story.split .cols{display:grid;grid-template-columns:1fr 1fr}` ตรวจโครงสร้าง ตรวจข้อความ ตรวจ `check.py` ผ่านหมด แล้วรายงานว่าเสร็จ

แต่ไฟล์เดียวกันนี้มี `.split{margin-top:40px;display:grid;grid-template-columns:1fr 54px 1fr}` อยู่ก่อนแล้ว เป็นของบล็อกอื่นในเว็บ พอใส่คลาสซ้ำชื่อ `.story` จึงกลายเป็นกริดสามคอลัมน์ ตัวเนื้อหาไปตกในช่องกลางที่กว้าง **54px** ผลคือย่อหน้าทั้งบล็อกเรียงลงมาคำละบรรทัด Noppadol เป็นคนไปเจอเองบนเว็บจริงหลัง publish แล้วส่งภาพหน้าจอมาให้ดู

**สิ่งที่ตรวจไปทั้งหมดไม่มีข้อไหนจับเรื่องนี้ได้เลย** เพราะทุกข้อตรวจ *เนื้อหา* ไม่มีข้อไหนตรวจ *การแสดงผล* Claude รู้ตัวด้วยซ้ำว่าเรนเดอร์หน้าเว็บดูเองไม่ได้ แต่ก็ยังรายงานว่าเสร็จโดยไม่หาทางดูให้ได้ก่อน

**กฎ** ก่อนตั้งชื่อคลาส CSS ใหม่ ต้อง `grep` ชื่อนั้นในไฟล์ก่อนเสมอ ถ้ามีอยู่แล้วให้เปลี่ยนชื่อ อย่าเอาไปซ้อนกับของเดิม และหลังเพิ่มกฎใหม่ทุกครั้ง ให้ไล่ดูว่ามี selector เดิมตัวไหนแมตช์ element เดียวกันได้อีกบ้าง

**กฎที่ตามมา** เมื่อแก้ layout ต้องยืนยันด้วยการวัดจริง ไม่ใช่แค่ดูโครงสร้าง วิธีที่ใช้ได้ในสภาพแวดล้อมนี้คือเปิดหน้าที่ publish อยู่ด้วย Chrome แล้ววัด `getComputedStyle` กับความกว้างจริงของกล่อง ถ้าหน้าที่จะแก้ยังไม่ขึ้นเว็บ ให้ inject CSS ที่กำลังจะใส่ลงไปในหน้าเก่าแล้วดูผลก่อน ตอนนี้ Chrome เปิด `file://` ไม่ได้ และ sandbox ติดตั้ง headless browser ไม่ได้ เพราะไม่มีสิทธิ์ลง system library

## 9 · `str.replace` ที่หาไม่เจอ ไม่ error มันแค่ไม่ทำอะไร

**เกิดขึ้น 2026-08-15** Claude สร้างหน้าเดโม `coffee-demo.html` จากแม่แบบ `coffee-farmer.html` แล้วแทรก CSS ของแดชบอร์ด 70 กฎด้วยบรรทัดนี้

```python
s = s.replace("\n.dlab{", "\n" + CSS + ".dlab{")
```

แต่แม่แบบไม่มีคลาส `.dlab` เลยสักตัว `replace` จึงคืนสตริงเดิมกลับมาเงียบ ๆ ไม่มี error ไม่มี warning สคริปต์รันจบสวยงาม พิมพ์ว่า *สร้าง coffee-demo.html · 87 KB* แล้ว Claude ก็รายงานว่าเสร็จ

**การตรวจที่ทำไปทั้งหมดผ่านหมด** แท็กสมดุล `check.py` ผ่าน jsdom ไม่มี error จุดบนแผนที่ครบ 43 คลิกแล้วแผงเปลี่ยนถูก เพราะ **JS ทำงานปกติ มีแต่ CSS ที่หายไปทั้งก้อน** Noppadol เปิดหน้าแล้วเจอข้อความเรียงเป็นแถวเปล่า ๆ กับแผนที่โลกสีดำทึบ

Claude มี `getComputedStyle` ใน jsdom อยู่ในมือตั้งแต่ต้น ใช้ตรวจ JS ไปแล้วด้วยซ้ำ แต่ไม่ได้เอามาตรวจ CSS สักบรรทัด

**กฎ** ทุกครั้งที่สคริปต์ประกอบไฟล์ด้วย `replace` หรือ `re.sub` ต้องพิสูจน์ว่าการแทรกเกิดขึ้นจริง ไม่ใช่เชื่อว่าสำเร็จ วิธีที่ใช้อยู่ตอนนี้คือด่านท้ายสคริปต์ที่นับชิ้นส่วนทุกอย่างในไฟล์ผลลัพธ์ แล้ว `sys.exit` ถ้าขาด

```python
checks = {"กฎ CSS": s.count(".dm-stat{") == 1,
          "CSS อยู่ในบล็อก style": s.index(".dm-stat{") < s.index("</style>"), ...}
if [k for k, ok in checks.items() if not ok]: sys.exit(...)
```

**กฎที่ตามมา** ก่อนบอกว่าหน้าใหม่เสร็จ ให้โหลดด้วย jsdom แล้วเรียก `getComputedStyle` กับคลาสหลักทุกตัว ถ้า `display` หรือ `position` ออกมาเป็นค่า default แปลว่า CSS ไม่ติด และเลือกจุดยึดสำหรับแทรกจากสิ่งที่มีจริงในแม่แบบเสมอ เช่น `</style>` ไม่ใช่คลาสที่บังเอิญนึกออก

## 11 · กฎ CSS ที่ปิดปีกกาไม่ครบ จะกลืนทุกกฎที่ตามหลังมันเงียบ ๆ

**เกิดขึ้น 2026-08-23** Noppadol เปิดเว็บจริงแล้วเจอแถบเมนูบนสุดกางออกมาทั้งชุด รายการย่อยทุกอันเรียงต่อกันเป็นพืด `The idea01 · The problem02 · What is MKM ?…` ล้นเป็นสองบรรทัด ทั้งที่ไม่กี่นาทีก่อนหน้านั้นผมเพิ่งรายงานว่าตรวจผ่าน 2,166 ข้อ

ต้นเหตุคือสคริปต์แบ่งหน้ากาแฟยกกฎ CSS ของปุ่มก่อนหน้า/ถัดไปมาจากอีกหน้าหนึ่งด้วย regex

```python
rules = re.findall(r"(?:@media[^{]*\{[^{}]*\.pn[^}]*\}[^}]*\}|\.pn[a-z-]*[^{]*\{[^}]*\})", st)
```

regex ตัดกฎธรรมดาได้ แต่ **ตัด `@media` ไม่ได้ เพราะมันซ้อนอีกชั้น** สิ่งที่ได้มาคือ

```css
@media(max-width:640px){.pn-in{grid-template-columns:1fr}.pn a.nx{text-align:left}
```

ขาดปีกกาปิดตัวสุดท้ายไปหนึ่งตัว แล้วสคริปต์ตัวถัดมาเอากฎเมนูย่อยไปต่อท้ายก้อนนี้พอดี **กฎเมนูย่อยทั้งชุดจึงตกไปอยู่ในเงื่อนไข `max-width:640px`** จอกว้างกว่านั้นไม่ได้รับกฎเลย แผงที่ควรซ่อนจึงกางค้างอยู่บนแถบเมนู

**ทำไมด่านตรวจ 2,166 ข้อไม่จับ** เพราะทุกข้อถามว่า *กฎอยู่ในไฟล์ไหม* ซึ่งอยู่ครบทุกบรรทัด ไม่มีข้อไหนถามว่า *กฎนั้นมีผลจริงไหม* และ `getComputedStyle` ของ jsdom ก็ตอบถูกต้องตามที่ CSS เขียนไว้ คือในบริบทที่ไม่มี viewport มันไม่ประเมิน media query ผมจึงอ่านค่าที่ถูกออกมาจากไฟล์ที่ผิด

**เปิดโค้ดดูก็ไม่เห็น** เพราะบรรทัดที่หายไปคือปีกกาตัวเดียวท้ายบรรทัดยาว 90 ตัวอักษร ต้องนับเอา ไม่ใช่มองเอา

**กฎ** ห้ามตัด CSS ด้วย regex เมื่อกฎนั้นอาจซ้อนชั้น ให้ไล่นับปีกกาแทน

```python
def rules_of(css):
    out, buf, depth = [], "", 0
    for ch in css:
        buf += ch
        if ch == "{": depth += 1
        elif ch == "}":
            depth -= 1
            if depth == 0: out.append(buf.strip()); buf = ""
    return [r for r in out if r]
```

**กฎที่ตามมา** ทุกสคริปต์ที่แตะ CSS ต้องมีด่านที่นับปีกกาในบล็อก `<style>` ให้สมดุลก่อนเขียนไฟล์ และด่านนี้ถูกใส่ไว้ใน `.tools/check.py` แล้ว ทุกหน้า ทุกรอบ ก่อน publish — เพราะร้อยแก้วที่ต้องอาศัยความจำจะล้มซ้ำ โค้ดที่รันเองไม่ล้ม

## 12 · ด่านตรวจถามว่า *ชี้ถูกไหม* แต่ไม่เคยถามว่า *มีกี่อัน*

**เกิดขึ้น 2026-08-23** Noppadol ส่งภาพหน้าจอมาบอกว่าเมนู `01 · MKM for Coffee` ค้างเป็นสีเขียว

  ที่ชี้มาที่หน้านี้ ซึ่งมีทั้งหัวกลุ่ม เมนูย่อย เมนูสไลด์ และปุ่มสลับภาษาสองชุด

ด่านรวมของ `sync_nav.py` มีสองข้อ คือ *มีตัวบ่งชี้ไหม* กับ *ลิงก์ในเมนูตายไหม*

**กฎ** ตัวบ่งชี้สถานะทุกชนิด ด่านตรวจต้องมีสามข้อ ไม่ใช่ข้อเดียว

```python
"มี":       nav.count(AC) >= 1
"ชี้ถูก":    f'{AC} href="{name}"' in nav
"ไม่เกิน":   nav.count(AC) == 1        # ข้อที่ขาดมาตลอด
```

**กฎที่ตามมา** เมื่อเจ้าของบอกว่าเห็นอะไรผิด แล้วผลวัดบอกว่าถูก **อย่าปิดเรื่องด้วยผลวัด**
ผลวัดที่ถูกแปลว่าคำถามที่ถามยังไม่ใช่คำถามเดียวกับที่เขาเห็น ให้ไปหาว่าอะไรที่ยังไม่ได้วัด
รอบนี้สิ่งที่ยังไม่ได้วัดคือ *ความสม่ำเสมอระหว่างหน้าในกลุ่มเดียวกัน* ซึ่งดูทีละหน้าไม่มีวันเห็น

เมื่อถูกถามว่างานล่าสุดคืออะไร ให้เปิดเซสชันที่ใหม่กว่าคำตอบที่กำลังจะให้ **ทุกอัน** ไม่ใช่เฉพาะอันที่ชื่อดูเข้าเค้า
อ่านแค่ข้อความสุดท้ายของแต่ละอันก็พอ ถูกกว่าการเดาผิดแล้วให้เจ้าของมาทักสามรอบมาก

**กฎที่ตามมา** ก่อนพูดคำว่า *ล่าสุด* ต้องตอบให้ได้ก่อนว่า **ล่าสุดเทียบกับอะไร** และดูครบทุกที่ที่งานอาจอยู่
รีโปเว็บ · เอกสารที่ทำในเซสชันแล้วไม่ได้ลงรีโป · รีโป `neogens-briefing-worker`
ถ้าดูไม่ครบ ให้บอกตรง ๆ ว่าดูจากที่ไหนบ้าง อย่าพูดลอย ๆ ว่า "งานล่าสุดคือ…"

## 15 · แก้ไฟล์ที่เป็นผลลัพธ์ แล้วเครื่องมือรายงานว่า "0 หน้า" เหมือนสำเร็จ

**เกิดขึ้น 2026-08-31** เติมลิงก์หน้าใหม่เข้า footer โดยแก้ที่ `.tools/shell/footer.en.html`
กับ `footer.th.html` เพราะ `HANDOFF.md` เขียนไว้เองว่า *footer มีต้นฉบับเดียวต่อภาษาแล้ว
แก้ที่นั่นแล้วรัน `build_footer.py`* แล้วรันสคริปต์ ผลที่ได้คือ

```
เขียน footer ใหม่ 0 หน้า จาก 48 หน้า · ด่านตรวจ 480 ข้อ · ไม่ผ่าน 0
✓ ทุกหน้าใช้ footer ชุดเดียวกัน · ห้าคอลัมน์ตรงกับเมนูบน · ไม่มีลิงก์ตาย
```

**บรรทัดนั้นมีเครื่องหมายถูก มีเลข 480 และไม่มีคำว่า error** อ่านผ่าน ๆ เหมือนงานเสร็จ
ความจริงคือ `.tools/shell/footer.*.html` เป็น **ผลลัพธ์** ไม่ใช่ต้นฉบับ ต้นฉบับจริงคือ
ตัวแปร `COLS` ในตัว `build_footer.py` เอง สคริปต์จึงสร้าง footer เดิมทับสิ่งที่เพิ่งแก้
แล้วพบว่าทุกหน้าตรงกับของเดิมอยู่แล้ว จึงเขียนใหม่ 0 หน้า อย่างถูกต้องตามหน้าที่มัน

เจอเพราะบังเอิญไปนับลิงก์ในหน้าจริงทีละหน้าต่อ ไม่ใช่เพราะเครื่องมือบอก
ถ้าเชื่อบรรทัดสรุปนั้น ลิงก์ใน footer จะหายไปทั้ง 48 หน้าโดยที่ทุกด่านขึ้นเขียว

**นี่คือข้อ 9 ในรูปใหม่** คราวนี้ไม่ใช่ `replace` ที่หาไม่เจอ แต่เป็นสคริปต์ที่ทำงานถูก
บนไฟล์ที่ผิด และ **ข้อ 1 ในรูปใหม่ด้วย** คราวนี้เอกสารที่เชื่อไม่ใช่เอกสารเก่าลอย ๆ
แต่คือ `HANDOFF.md` ของโปรเจกต์เอง ซึ่งเขียนที่อยู่ของต้นฉบับไว้ผิด และไม่มีใครไปแก้

**กฎ** ก่อนแก้ไฟล์ที่เอกสารบอกว่าเป็น "ต้นฉบับ" ให้ `grep` หาก่อนว่ามีสคริปต์ตัวไหน
`write_text` ลงไฟล์นั้นบ้าง ถ้ามี แปลว่ามันคือผลลัพธ์ ต้นฉบับอยู่ในสคริปต์ตัวนั้น

**กฎที่ตามมา** ตัวเลข 0 ในรายงานของเครื่องมือ ให้ถือเป็นคำเตือนเสมอ ไม่ใช่คำยืนยัน
*เขียนใหม่ 0 หน้า* หลังจากเพิ่งแก้ต้นฉบับ แปลว่าอย่างใดอย่างหนึ่งผิด และก่อนบอกว่า
งานเสร็จ ต้องยืนยันจากไฟล์ปลายทางจริง ไม่ใช่จากบรรทัดสรุปของเครื่องมือ

## สรุปสั้นที่สุด

ห้าข้อแรกเป็นโรคเดียวกัน คือ Claude ตอบจากสิ่งที่คิดว่าน่าจะเป็น แทนที่จะไปดูสิ่งที่เป็นอยู่จริง และเลือกทำแทนเจ้าของแทนที่จะถาม

ข้อ 5 เพิ่มอีกชั้นหนึ่ง คือกฎที่ตัวเองเขียนก็ยังข้ามได้ ถ้าตีความให้มันเริ่มบังคับใช้ช้ากว่าจุดที่ความเสียหายเกิด

ข้อ 6 เพิ่มชั้นที่สาม คือเครื่องมือส่งเสียงเตือนมาแล้ว แต่ Claude อ่านผ่าน แล้วปล่อยให้เจ้าของไปเจอความพังเอง

ข้อ 8 เพิ่มชั้นที่สี่ คือตรวจครบทุกข้อแล้วก็ยังพลาดได้ ถ้าทุกข้อที่ตรวจอยู่คนละเรื่องกับสิ่งที่พัง ตรวจเนื้อหาสิบรอบก็ไม่เจอความพังของการแสดงผล

ข้อ 9 เพิ่มชั้นที่ห้า คือเครื่องมือที่ล้มเหลวโดยไม่ส่งเสียง อันตรายกว่าเครื่องมือที่พัง และ Claude ถือเครื่องมือที่จะจับมันได้อยู่ในมือแล้ว แต่ไม่ได้หยิบมาใช้

ข้อ 10 เพิ่มชั้นที่หก คือด่านตรวจที่ถามแต่ว่าของใหม่มาครบไหม จะไม่มีวันเห็นของเก่าที่ไม่ควรอยู่ ทุกชุดตรวจต้องมีทั้งข้อ *มีครบ* และข้อ *ไม่เหลือ*

ข้อ 11 เพิ่มชั้นที่เจ็ด คือด่านตรวจสองพันข้อก็ยังพลาดได้ ถ้าทุกข้อถามว่า *ของอยู่ในไฟล์ไหม* โดยไม่มีข้อไหนถามว่า *ของนั้นมีผลจริงไหม* — และเครื่องมือวัดที่ตอบถูกตามไฟล์ที่ผิด ก็ยังให้คำตอบที่ผิดอยู่ดี

ข้อ 12 เพิ่มชั้นที่แปด คือผลวัดที่ถูกต้องใช้ปิดเรื่องที่เจ้าของเห็นไม่ได้ ถ้าคำถามที่วัดยังไม่ใช่คำถามเดียวกับที่เขาเห็น *ชี้ถูกไหม* กับ *มีกี่อัน* เป็นคนละคำถาม และข้อหลังคือข้อที่ไม่มีใครถาม

ข้อ 13 เพิ่มชั้นที่เก้า คือด่านที่ตั้งไว้กันความพลาดจะไม่ทำงานเลย ถ้าตีความว่างานที่ดูเบาไม่ต้องผ่านด่าน และงานที่ดูเบาที่สุด คือคำถามว่า *ค้างอะไรอยู่* ซึ่งเป็นคำถามที่ด่านนี้เกิดมาเพื่อมันโดยตรง

ข้อ 14 เพิ่มชั้นที่สิบ คือการค้นที่คัดของออกด้วยป้ายชื่อแทนที่จะเปิดดู จะไม่มีวันเจอสิ่งที่ชื่อไม่ตรงกับที่คิด และคำว่า *ล่าสุด* ที่ดูจากที่เดียว คือคำตอบที่ผิดโดยที่หน้าตาไม่ผิด

ข้อ 15 เพิ่มชั้นที่สิบเอ็ด คือเครื่องมือที่ทำงานถูกต้องทุกบรรทัดบนไฟล์ที่ผิด จะรายงานความสำเร็จออกมาอย่างซื่อสัตย์ และเอกสารของโปรเจกต์เองก็ตกยุคได้ ไม่ต่างจากเอกสารอื่น *เขียนใหม่ 0 หน้า* หลังเพิ่งแก้ต้นฉบับ คือเสียงเตือน ไม่ใช่เสียงยืนยัน
