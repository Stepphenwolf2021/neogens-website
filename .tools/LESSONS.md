# บทเรียนของ Claude — โปรเจกต์ neogens-website

ทุกข้อในไฟล์นี้มาจากความผิดพลาดจริงที่เกิดขึ้นกับโปรเจกต์นี้ ไม่ใช่กฎที่คิดขึ้นลอย ๆ
ไฟล์นี้เพิ่มได้เรื่อย ๆ ห้ามลบข้อเก่าออกแม้จะรู้สึกว่าไม่พลาดอีกแล้ว

**จำนวนบทเรียนตอนนี้ 7 ข้อ**

Claude ต้องอ่านไฟล์นี้จนจบก่อนตอบอะไรก็ตามในโปรเจกต์นี้ แล้วขึ้นต้นข้อความแรกของเซสชันด้วยบรรทัดนี้

> อ่าน `.tools/LESSONS.md` แล้ว — 7 ข้อ

ถ้าไม่มีบรรทัดนี้ แปลว่ายังไม่ได้อ่าน Noppadol ทักได้ทันที

---

## 1 · อย่าสรุปสถานะงานจากเอกสารใน Context ให้ไปดูของจริงก่อน

**เกิดขึ้น 2026-08-14** Noppadol ถามว่า "สรุปงานเว็บไซต์ที่ค้างอยู่" Claude อ่านเอกสารรากฐานใบเดียวที่อยู่ใน Context แล้วตอบว่ายังไม่ได้ลงมือทำเว็บเลย ยังเหลืออีก 6 ข้อที่ต้องตัดสินใจก่อนเริ่ม

ความจริงคือ `neogens.co` ขึ้นไปนานแล้ว เป็นเว็บ 13 หน้าต่อภาษา สองภาษา มีธีมสลับ มีบทความยาว มี `check.command` และ `publish.command` ใช้งานได้จริง Claude สรุปผิดทั้งหมด เพราะเอกสารใน Context เขียนไว้ตั้งแต่ก่อนลงมือ แล้วไม่มีใครไปอัปเดตมัน

**นี่คือหลักการข้อ 6 ของบริษัทเอง** แผนที่ไม่ใช่ดินแดน Claude อธิบายทุกอย่างได้อย่างสมเหตุสมผลจากแผนที่ที่ล้าสมัย

**กฎ** ก่อนตอบคำถามว่า *ค้างอะไร* หรือ *สถานะเป็นอย่างไร* หรือ *ทำอะไรไปแล้วบ้าง* ต้องทำสามอย่างนี้ก่อน ห้ามข้าม

1. อ่านไฟล์จริงในรีโป และดู `git log`
2. เปิด `neogens.co` ของจริงขึ้นมาดู
3. ไล่ transcript เซสชันเก่าที่เกี่ยวข้อง ด้วย `list_sessions` แล้ว `read_transcript`

เอกสารใน Context บอกได้แค่ว่าเคยตั้งใจจะทำอะไร ไม่ได้บอกว่าทำไปแล้วแค่ไหน

## 2 · อ่านสคริปต์ให้จบก่อนให้คำแนะนำเรื่องสคริปต์

**เกิดขึ้น 2026-08-14** Claude เห็นโฟลเดอร์ `card/` ที่ยังไม่ถูก track แล้วเตือนว่า `publish.command` ใช้ `git add -A` เดี๋ยวจะกวาดไฟล์นามบัตรขึ้น GitHub ด้วย พร้อมเสนอให้ Noppadol ย้ายโฟลเดอร์ออกเองหรือแก้ `.gitignore` ก่อน

แต่ `.tools/publish.sh` มีด่านนี้อยู่แล้วตั้งแต่ต้น ขั้น 3/5 มันโชว์ diff stat แล้วพิมพ์ว่า "Read the list above. If you see a file you did not mean to touch, answer N" ถ้าตอบ N มันจะ `git reset` คืนให้เอง Claude สั่งงานซ้อนกลไกที่ออกแบบมาเพื่อเรื่องนี้พอดี เพราะอ่านแค่บรรทัด `git add -A` แล้วหยุด

**กฎ** ก่อนพูดถึงพฤติกรรมของ `check.command` `publish.command` `.tools/publish.sh` หรือ `.tools/check.py` ต้องอ่านไฟล์นั้นทั้งไฟล์ก่อน ห้าม grep แล้วเดาจากบรรทัดเดียว

**กฎที่ตามมา** วิธีทำงานที่ตกลงกันไว้คือ Noppadol ดับเบิลคลิก `check.command` แล้วตามด้วย `publish.command` ไม่ใช่พิมพ์คำสั่งใน terminal อย่ายื่นคำสั่ง git ให้เขารันเอง นอกจากเขาจะขอ และ Claude แก้ไฟล์อย่างเดียว ไม่ commit ไม่ push

## 3 · ข้อความที่ Noppadol เขียนมาเอง ห้ามแก้แม้แต่ตัวเดียว

**เกิดขึ้น 2026-08-14** Noppadol ส่งเนื้อหาหน้าแรก 11 ย่อหน้ามาให้ขึ้นเว็บ Claude เอาขึ้นแล้วแก้ของเขาไปหลายจุดโดยไม่ได้ขออนุญาต

| Claude แก้เป็น | ของจริงที่เขาเขียน |
|---|---|
| ล็อก | ล็อค |
| อินเทอร์เน็ต | อินเตอร์เน็ต |
| hallucination | Halluciations |
| ตัดทิ้ง | ใช้งบลงทุนไปมากมาย · สั่งสมมานานหลายสิบปี |
| บริหารความรู้ของตัวเองได้ดีแค่ไหน | ความสามารถในการบริหารจัดการความรู้ของตัวเอง |

Claude อ้างสกิล `neogens-thai-voice` กับกฎเรื่องห้ามใส่ตัวเลขที่ยืนยันไม่ได้ แล้วรายงานทีหลังว่า "สามจุดที่ผมตัดสินใจแทน" ซึ่งตอนนั้นแก้ไปเรียบร้อยแล้ว

**สกิลภาษาไทยใช้กับข้อความที่ Claude เขียนเอง ไม่ใช่กับข้อความที่เจ้าของเขียนมา**

**กฎ** เมื่อ Noppadol ส่งข้อความมาให้ขึ้นเว็บ ให้วางลงไปตรง ๆ ทุกตัวอักษร รวมทั้งตัวสะกดที่ดูเหมือนพิมพ์ผิด ถ้าเห็นอะไรที่คิดว่าควรแก้ ให้ถามก่อนแล้วรอคำตอบ ห้ามแก้แล้วค่อยรายงาน

เสร็จแล้วให้ตรวจย้อนด้วยการเทียบตัวอักษรว่าทุกย่อหน้าอยู่ในไฟล์จริงครบ แล้วรายงานผลการเทียบให้ดู

ถ้าจำเป็นต้องมีข้อความที่เจ้าของไม่ได้ส่งมา เช่น หัวการ์ด ให้ยกวลีออกมาจากประโยคของเขาเอง ห้ามแต่งใหม่ และต้องบอกให้ชัดว่าส่วนไหนไม่ใช่คำของเขา

## 4 · ถ้าคำสั่งที่ได้รับจะทำให้ผลลัพธ์ขัดกันเอง ให้ทักก่อนลงมือ

**เกิดขึ้น 2026-08-14** Claude ถามสองคำถามเรื่องเปลี่ยนป้ายเมนู คำตอบที่ได้คือ *เปลี่ยนทุกที่* กับ *เปลี่ยนหัวกลุ่มเป็น MKM ด้วย* ซึ่งพอเอามารวมกันจะได้หัวกลุ่มกับรายการใต้มันเป็นข้อความเดียวกันเป๊ะ สองบรรทัดติดกัน Claude เลือกทางที่สามเองเงียบ ๆ แล้วค่อยรายงานทีหลังว่าตัดสินใจแทนไปแล้ว

**กฎ** เจอคำสั่งที่ขัดกันเอง หรือให้ผลที่เจ้าของน่าจะไม่ได้ตั้งใจ ให้หยุดแล้วทักทันทีพร้อมเสนอทางออก อย่าเลือกเองแล้วรายงานย้อนหลัง การรายงานทีหลังไม่ใช่การขออนุญาต

## 5 · ด่านบังคับต้องผ่านก่อนพิมพ์ตัวอักษรแรก ไม่ใช่ก่อนแก้ไฟล์

**เกิดขึ้น 2026-08-15** วันถัดจากวันที่ตั้งด่านนี้ขึ้นมาเอง Noppadol ทักว่า "สวัสดีตอนเช้า มาเริ่มงานกัน" Claude ยังไม่ได้อ่านไฟล์นี้ แต่ตอบไปแล้วว่า *"เอกสารรากฐานระบุไว้ชัดว่ามี 6 เรื่องที่ต้องตัดสินก่อนลงมือทำเว็บ ยังค้างอยู่"*

นั่นคือความผิดข้อ 1 คำต่อคำ ทั้งที่ข้อ 1 ถูกเขียนขึ้นเพราะความผิดอันนี้พอดีเมื่อวันก่อนหน้า

สาเหตุที่ด่านไม่ทำงานคือ Claude ตีความคำว่า "ก่อนเริ่มงาน" เป็นก่อนแก้ไฟล์ ไม่ใช่ก่อนพูด จึงทักทายและสรุปสถานะไปก่อน แล้วค่อยไปอ่านทีหลัง **แต่ความเสียหายของข้อ 1 เกิดที่ประโยคแรก ไม่ได้เกิดที่การแก้ไฟล์**

**กฎ** ห้ามพิมพ์อะไรทั้งสิ้นก่อน `Read` ไฟล์นี้จบ รวมทั้งคำทักทาย คำถามกลับ และการสรุปสถานะ บรรทัด "อ่าน `.tools/LESSONS.md` แล้ว — N ข้อ" ต้องเป็นข้อความแรกที่ออกมา ไม่ใช่ข้อความที่สอง

**กฎที่ตามมา** ถ้าเผลอตอบไปก่อนแล้ว ให้ถอนคำนั้นออกมาตรง ๆ ทันทีที่อ่านจบ อย่าปล่อยคำตอบที่ผิดค้างไว้ในบทสนทนาเฉย ๆ แล้วเดินหน้าต่อเหมือนไม่มีอะไรเกิดขึ้น

## 6 · `git status` กับ `git diff` ไม่ใช่คำสั่งอ่านอย่างเดียว มันทิ้งไฟล์ล็อคไว้

**เกิดขึ้น 2026-08-15** Claude รัน `git diff --stat` เพื่อตรวจงานตัวเองว่าแก้อะไรไปบ้าง คำสั่งนั้นสร้าง `.git/index.lock` ขึ้นมาแล้วลบตัวเองไม่ได้ เพราะสิทธิ์ในกล่องที่ Claude รันคำสั่งไม่ตรงกับสิทธิ์บนเครื่อง ตอนนั้นมี warning ขึ้นว่า `unable to unlink .git/index.lock` แต่ Claude อ่านผ่านไป

ผลคือ Noppadol กด `publish.command` แล้วมันตายที่ขั้น 3/5 ว่า **`Unable to create '.git/index.lock': File exists`** เสียเวลาเปล่าไปหนึ่งรอบ กับความผิดที่ตัวเองก่อไว้เงียบ ๆ ตั้งแต่ก่อนหน้านั้น

`git status` และ `git diff` หน้าตาเหมือนคำสั่งที่แค่อ่าน แต่ทั้งคู่เขียน `index.lock` ตอน refresh index ส่วน `git log` กับ `git show` ไม่แตะ index จึงปลอดภัย

**กฎ** ถ้าต้องเรียก `git status` หรือ `git diff` ในโปรเจกต์นี้ ให้ใส่ `--no-optional-locks` เสมอ

```
git --no-optional-locks status --short
git --no-optional-locks diff --stat
```

**กฎที่ตามมา** ก่อนจบทุกครั้งที่แตะ git ให้เช็กว่า `.git/index.lock` ไม่มีอยู่ ถ้ามีต้องลบก่อนบอกว่างานเสร็จ และเจอ warning จาก git เมื่อไร ห้ามอ่านผ่าน เพราะข้อ 4 ของบริษัทเองเขียนไว้ว่าความเงียบคือศัตรู ตรงนี้ git ส่งเสียงเตือนแล้ว คนที่เงียบคือ Claude

## 7 · เวลาของพัง ให้ถามก่อนว่าเปิดจากที่ไหน อย่าเพิ่งไปไล่ทฤษฎี

**เกิดขึ้น 2026-08-15** ฟอร์มบนหน้ากาแฟส่งไม่ผ่าน Claude ไล่หาสาเหตุอยู่สามรอบ ตั้งทฤษฎีว่าเป็นการจำกัดอัตรา 429 แก้ Worker ขยับโควตาจาก 5 เป็น 20 เขียนเทสต์เพิ่ม แล้วให้ Noppadol deploy ใหม่

พอขอภาพหน้าจอ Network tab มาดู คำตอบอยู่บนแถบที่อยู่บรรทัดแรกสุด — เขาเปิดไฟล์ด้วย `file:///Users/...` ไม่ใช่จาก `https://www.neogens.co` หน้าที่เปิดแบบนี้ส่ง Origin เป็น `null` Worker จึงตีกลับเป็น CORS error ตั้งแต่ด่านแรก **ไม่ใช่บั๊ก และไม่มีอะไรต้องแก้เลย**

**สิ่งที่ทำให้เรื่องนี้แย่กว่าการเดาผิดธรรมดา** คือ Claude เขียนคำเตือนเรื่องนี้ไว้เองในรายงานก่อนหน้า คำต่อคำว่า *"ฟอร์มจะไม่ทำงานถ้าเปิดไฟล์จากเครื่อง เปิด local จะได้ 403"* แล้วพอมันเกิดขึ้นจริง กลับไม่ได้ย้อนไปอ่านสิ่งที่ตัวเองเพิ่งเขียน

**กฎ** เจอรายงานว่าของบนเว็บพัง คำถามแรกคือ **เปิดจาก URL ไหน** ถามก่อนตั้งทฤษฎีใด ๆ ทั้งสิ้น และก่อนแก้โค้ดแม้แต่บรรทัดเดียว

**กฎที่ตามมา** ขอหลักฐานตรง ๆ ก่อนเดา — ภาพหน้าจอ Network tab หรือค่าสถานะจริง ใช้เวลาน้อยกว่าการไล่ทฤษฎีมาก และอย่าลืมย้อนอ่านคำเตือนที่ตัวเองเขียนไว้เองในบทสนทนาเดียวกัน

## สรุปสั้นที่สุด

ห้าข้อแรกเป็นโรคเดียวกัน คือ Claude ตอบจากสิ่งที่คิดว่าน่าจะเป็น แทนที่จะไปดูสิ่งที่เป็นอยู่จริง และเลือกทำแทนเจ้าของแทนที่จะถาม

ข้อ 5 เพิ่มอีกชั้นหนึ่ง คือกฎที่ตัวเองเขียนก็ยังข้ามได้ ถ้าตีความให้มันเริ่มบังคับใช้ช้ากว่าจุดที่ความเสียหายเกิด

ข้อ 6 เพิ่มชั้นที่สาม คือเครื่องมือส่งเสียงเตือนมาแล้ว แต่ Claude อ่านผ่าน แล้วปล่อยให้เจ้าของไปเจอความพังเอง

> ระบบที่ยอมแพ้อย่างเงียบ ๆ อันตรายกว่าระบบที่พัง เพราะระบบที่พังอย่างน้อยก็บอกเรา
