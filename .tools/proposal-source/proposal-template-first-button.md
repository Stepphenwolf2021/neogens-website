# ข้อเสนอโครงการ · กลัดกระดุมเม็ดแรก

**แม่แบบ · สำหรับองค์กรด้านความรู้**
Neo Gens Co., Ltd. · [วันที่]

> วิธีใช้แม่แบบนี้ ทุกที่ที่อยู่ในวงเล็บเหลี่ยมคือช่องที่ต้องเติมด้วยของจริงขององค์กรนั้น
> **ห้ามเติมด้วยการเดา** ตัวเลขทุกตัวในข้อเสนอต้องมาจากการตรวจหน้าจริงที่ทำซ้ำได้
> ส่วนที่เป็นผลตรวจ ให้แนบวิธีทำซ้ำไปด้วยเสมอ เพราะข้อเสนอทั้งฉบับตั้งอยู่บนคำว่าตรวจสอบได้

## 1 · ทำไมเราติดต่อมา

[ชื่อองค์กร] ตั้งขึ้นมาเพื่อ [พันธกิจตามที่องค์กรประกาศไว้เอง — ยกคำของเขามา ไม่ใช่คำเรา]

เว็บไซต์ขององค์กรคือสิ่งที่คนภายนอกใช้ตัดสินว่าองค์กรนี้รู้อะไรและน่าเชื่อถือแค่ไหน และทุกวันนี้คนภายนอกไม่ได้มีแต่คน ระบบค้นหาและผู้ช่วย AI อ่านเว็บก่อนคนเสมอ แล้วสรุปให้คนฟังอีกที

เราตรวจหน้าเว็บของ [ชื่อองค์กร] จากภายนอก ด้วยเครื่องมือสาธารณะ ไม่ได้ขอข้อมูลหรือสิทธิ์เข้าถึงใด ๆ ผลที่ได้คือ [สรุปหนึ่งประโยค]

ข้อเสนอฉบับนี้ไม่ใช่การเสนอทำเว็บใหม่ เป็นการเสนอ **กลัดกระดุมเม็ดแรกให้ตรงรู** ในเวลาสั้น ๆ และวัดผลก่อนหลังได้ด้วยเครื่องมือเดียวกันที่ใครก็เปิดดูได้

## 2 · สิ่งที่ตรวจพบ

ตรวจเมื่อ [วันเวลา] ด้วย [เครื่องมือ] และการอ่านโครงสร้างหน้าโดยตรง

| สิ่งที่ตรวจ | สิ่งที่ควรมี | สิ่งที่พบ |
|---|---|---|
| ข้อมูลที่มีโครงสร้าง (JSON-LD) | ประกาศว่าองค์กรนี้คือใคร | [ผล] |
| หน้าแรกที่คนและเครื่องเข้าถึง | หน้าเดียว มีเนื้อหา | [ผล] |
| `robots.txt` | มี บอกทางให้บอต | [ผล] |
| `sitemap.xml` | มี บอกว่ามีหน้าอะไรบ้าง | [ผล] |
| `canonical` | มีทุกหน้า | [ผล] |
| `hreflang` | ผูกคู่ภาษา | [ผล] |
| หัวเรื่องหลักของหน้า | หนึ่งอันต่อหน้า | [ผล] |

**วิธีทำซ้ำ** เปิด `search.google.com/test/rich-results` วางที่อยู่หน้าแรกขององค์กรลงไป กดทดสอบ ใช้เวลาประมาณสามสิบวินาที ไม่ต้องสมัคร ไม่ต้องติดตั้งอะไร

สิ่งที่ควรดูไม่ใช่คำว่าผ่านหรือไม่ผ่าน แต่คือบรรทัดที่บอกว่าตรวจพบอะไร

## 3 · ทำไมเรื่องนี้สำคัญกับองค์กรที่ทำงานด้านความรู้

องค์กรทั่วไปที่เว็บไม่ได้ประกาศโครงสร้าง เสียโอกาสถูกค้นเจอ

องค์กรที่ประกาศตัวเป็นผู้นำด้านความรู้ เสียมากกว่านั้น เพราะสิ่งที่เว็บบอกกับเครื่อง คือคำแถลงขององค์กรเอง ถ้าเว็บไม่ได้บอกว่าองค์กรนี้คือใคร ทำเรื่องอะไร และของแต่ละชิ้นเกี่ยวกันอย่างไร เครื่องจะเดาแทน แล้วเอาคำเดานั้นไปตอบคนที่ถามหาความรู้ในสาขาที่องค์กรนี้เป็นเจ้าของเรื่อง

สามอย่างที่เสียไปโดยไม่มีใครแจ้ง

```
1  คนที่กำลังหาสิ่งที่องค์กรมีอยู่จริง หาไม่เจอ หรือเจอของคนอื่นก่อน
2  ผู้ช่วย AI ตอบคำถามในสาขานี้ โดยอ้างแหล่งอื่นที่เขียนโครงสร้างไว้ชัดกว่า
3  ความรู้ที่ลงทุนสร้างมาหลายปี ใช้ต่อในระบบอื่นไม่ได้ เพราะไม่มีโครงให้เกาะ
```

**นี่ไม่ใช่ปัญหาของทีมเว็บ** คำถามที่ต้องตอบก่อนเขียนโครงสร้างสักบรรทัดคือคำถามขององค์กร ว่าอะไรคืออะไร และอะไรเกี่ยวกับอะไร ซึ่งมีแต่คนในองค์กรที่ตอบได้

## 4 · ข้อเสนอ · กลัดกระดุมเม็ดแรก

ไม่ทำทั้งเว็บพร้อมกัน เลือกหนึ่งส่วนกับหนึ่งคำถาม ทำตั้งแต่ต้นจนจบ แล้วค่อยขยาย
การพยายามทำทุกอย่างพร้อมกัน คือวิธีที่โครงการแบบนี้ตายมาแล้วนับไม่ถ้วน

### เฟส 0 · สำรวจและตกลงขอบเขต · [1 สัปดาห์]

- อ่านโครงสร้างเว็บปัจจุบันทั้งหมด บันทึกเป็นสถานะตั้งต้นที่ตรวจซ้ำได้
- เวิร์กช็อปครึ่งวันกับผู้บริหารและคนที่รู้โครงองค์กรจริง
- ตอบคำถามเดียว **องค์กรนี้จะประกาศตัวเองกับเครื่องว่าอะไร**
- ส่งมอบ บันทึกสถานะตั้งต้น + ขอบเขตงานที่ตกลงร่วมกัน

### เฟส 1 · ชั้นตั้งค่า · [2 สัปดาห์]

งานที่ไม่ต้องตัดสินใจอะไรใหม่ ทำแล้วเห็นผลทันที

- หน้าแรกที่คนพิมพ์ ต้องเป็นหน้าที่มีเนื้อหาจริง
- `robots.txt` และ `sitemap.xml`
- `canonical` ทุกหน้า
- `hreflang` จับคู่ภาษา ถ้ามีมากกว่าหนึ่งภาษา
- หัวเรื่องหลักหนึ่งอันต่อหน้า และคำอธิบายหน้าที่เขียนไว้จริง

### เฟส 2 · ชั้นความหมาย · [3 สัปดาห์]

- ออกแบบ ontology รอบแรกจากพันธกิจ ไม่ใช่จาก schema
- ตัดสินอัตลักษณ์ ว่าองค์กร หน่วยงานย่อย และบริการแต่ละตัว เป็นสิ่งเดียวกันหรือคนละสิ่ง
- ประกาศเป็น JSON-LD ที่เครื่องอ่านได้ ผูกกลับมาที่ตัวระบุชุดเดียว
- แถบเส้นทางที่คนเห็น ต้องสร้างจากโครงเดียวกับที่ประกาศกับเครื่อง ไม่ใช่สองชุด

### เฟส 3 · ส่งมอบและถ่ายทอด · [1 สัปดาห์]

- ผลตรวจก่อนและหลัง วางคู่กัน
- คู่มือให้ทีมขององค์กรทำต่อเองได้ และเกณฑ์ตรวจก่อนปล่อยหน้าใหม่
- เวิร์กช็อปส่งมอบครึ่งวัน

**รวม [7 สัปดาห์]** ปรับได้ตามขนาดของส่วนที่เลือกทำ

## 5 · สิ่งที่ส่งมอบ

```
1  บันทึกสถานะตั้งต้น        ผลตรวจจากเครื่องมือสาธารณะ ทำซ้ำได้ทุกบรรทัด
2  เอกสาร ontology รอบแรก   อะไรคืออะไร เกี่ยวกันอย่างไร ในภาษาที่คนอ่านรู้เรื่อง
3  โครงสร้างที่ติดตั้งแล้ว     บนเว็บจริง ไม่ใช่ในเอกสาร
4  ผลตรวจหลังทำ            วางคู่กับผลตั้งต้น
5  คู่มือและเกณฑ์ตรวจ        ให้ทีมขององค์กรทำต่อเอง
```

**ความสำเร็จของโครงการนี้ คือการที่ทีมของคุณขยายงานต่อเองได้** ไม่ใช่การที่เราต้องอยู่ต่อ

## 6 · สิ่งที่เราต้องการจากฝั่งคุณ

เวลาของผู้เชี่ยวชาญคุณคือต้นทุนจริงของงานนี้ ไม่ใช่ค่าจ้างเรา

```
ผู้บริหารที่ตัดสินได้        เวิร์กช็อป 2 ครั้ง ครั้งละครึ่งวัน
คนที่รู้โครงองค์กรจริง        เวิร์กช็อปทุกครั้ง และตอบคำถามระหว่างทาง
คนที่แก้เว็บได้จริง          สัปดาห์ละไม่เกิน 4 ชั่วโมง ตลอดโครงการ
```

ถ้าจัดเวลานั้นไม่ได้ งานจะไม่แข็งแรงพอ และเราขอบอกกันตั้งแต่ตอนนี้

---

## 7 · สิ่งที่เราไม่ทำ และไม่รับประกัน

- **ไม่รับประกันอันดับในผลค้นหา** ใครบอกว่ารับประกันได้คือกำลังขายของ สิ่งที่งานนี้ให้คือเครื่องเลิกเดา แล้วหันมาอ้างสิ่งที่องค์กรเขียนไว้เอง
- **ไม่รับงานแบบเหมาไปทำข้างนอกแล้วส่งของกลับมา** ถ้าอยากได้แบบนั้น เราไม่ใช่คู่ที่เหมาะ และงานแบบนั้นมักถูกทิ้งภายในปีเดียว
- **ไม่ทำทั้งองค์กรพร้อมกันในรอบเดียว**
- **AI ไม่ได้ทำงานแทนผู้เชี่ยวชาญ** ระบบเก็บข้ออ้างและหลักฐานไว้ แต่คนของคุณเป็นผู้ตัดสินว่าอะไรคือข้อเท็จจริง

---

## 8 · วัดผลอย่างไร

ไม่วัดด้วยความรู้สึก และไม่วัดด้วยตัวเลขที่เราเป็นคนนับให้ฝ่ายเดียว

```
ก่อนเริ่ม   ผลตรวจจากเครื่องมือสาธารณะ บันทึกวันเวลาไว้
ระหว่างทาง  รายงานรอบละสัปดาห์ พร้อมสิ่งที่ยังทำไม่ได้
เมื่อจบ     ผลตรวจชุดเดิม รันซ้ำ วางเทียบกัน
ต่อจากนั้น  ทีมของคุณรันเองได้ทุกเมื่อ ในสามสิบวินาที
```

## ภาคผนวก ก · อภิธานศัพท์

คำอย่าง `canonical` `hreflang` `robots.txt` `sitemap.xml` `JSON-LD` `schema.org`
`ontology` `knowledge graph` และคำอื่นที่ใช้ในเอกสารฉบับนี้ อธิบายไว้ครบใน
